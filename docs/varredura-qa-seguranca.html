🔴 Crítico — rotas internas abertas a qualquer um

Corrigido   commit e1a2c97
O que estava errado

As quatro rotas /api/agents/* e o webhook do Asaas só exigiam credencial quando a variável de ambiente existia:

if (CRON_SECRET) {           // ← sem a variável, nada é checado
  if (auth !== `Bearer ${CRON_SECRET}`) return 401;
}
// ...segue e executa

Ou seja: a proteção sumia justamente no ambiente onde alguém esqueceu de configurar. É o oposto do que o middleware.ts do /admin já fazia certo (sem credenciais, devolve 503 e não deixa passar).

Por que isso importava na sua produção

O CRON_SECRET não está configurado — eu mesmo recomendei não configurá-lo, por serem "coisas dos agentes em standby". Consequência concreta: /api/agents/prospeccao e /api/agents/conteudo estavam acessíveis publicamente e gravam no banco (outreach_drafts, content_drafts) e alteram o status dos prospects. Qualquer pessoa que descobrisse o endereço poderia inflar essas tabelas em série.

E havia uma bomba-relógio: no dia em que a ANTHROPIC_API_KEY fosse ligada na v2, cada chamada dessas rotas passaria a consumir IA paga — uma torneira de custo aberta para terceiros.

O que mudou

Criei lib/api-auth.ts com a regra de falhar fechando, aplicada nas cinco rotas. Sem segredo configurado a rota responde 503 e não executa nada.

CenárioAntesAgora
Sem segredo configurado200 — executava 😱503 — bloqueado
Com segredo, credencial errada401401
Com credencial correta200200

Os três cenários foram testados de verdade, subindo o servidor localmente com e sem as variáveis.

🟠 Alto — webhook aceitaria pagamento forjado

Corrigido   mesmo commit

O /api/webhooks/asaas tinha o mesmo padrão. Como o ASAAS_WEBHOOK_TOKEN está configurado hoje, ele estava protegido — mas bastava alguém apagar essa variável (ou recriá-la com nome errado, o que quase aconteceu com a do plano Básico) para o endereço ficar aberto.

O que um atacante conseguiria: enviar um PAYMENT_CONFIRMED falso e, com isso, gravar pagamentos inexistentes na tabela payments e disparar o e-mail "💰 Pagamento confirmado" para você. Não move dinheiro, mas envenena seu controle financeiro e sua confiança nos avisos.

Agora, sem o token configurado, o webhook responde 503 em vez de aceitar qualquer coisa.

⚠️ Atenção prática: o webhook depende do ASAAS_WEBHOOK_TOKEN estar presente. Se ele for removido da Vercel, as notificações do Asaas param (503) em vez de passar batido — é o comportamento desejado, mas é bom saber para não estranhar.

🟡 Médios

Vazamento de memória no limitador de requisições

Corrigido   commit e1a2c97

O lib/rate-limit.ts guarda uma entrada por IP num Map, mas nunca removia as expiradas. Cada visitante novo somava uma entrada permanente. Numa instância de vida longa, o consumo de memória só cresce.

Agora, ao passar de 10 mil chaves, faz uma faxina removendo as janelas vencidas.

Dependências com falhas conhecidas

Parcial   commit 4145ffd

O npm audit apontava 4 falhas de severidade alta. Apliquei a correção segura, que resolveu 2 delas (postcss — leitura arbitrária de arquivos .map). Build e lint seguem limpos.

As outras 2 continuam: vêm do sharp, que é dependência do próprio Next.js, e só saem atualizando para o Next 16 — uma mudança de versão maior, com risco de quebrar coisas.

Recomendação: não fazer agora. O sharp processa imagens, e o site não recebe imagens de usuários (o visual é CSS e SVG), então a exposição real é baixa. Vale agendar o upgrade do Next como tarefa própria, com tempo para testar.

🟢 Pontos de atenção — sem ação necessária

Limitador de requisições é por instância

O controle vive na memória de cada instância serverless. Com várias instâncias ativas, o limite real fica multiplicado. Protege contra abuso casual, mas não contra um ataque coordenado. Para o volume atual está adequado; se o tráfego crescer, o caminho é um limitador compartilhado (Upstash/Redis).

CSP permite unsafe-inline em scripts

Necessário para o Next.js (JSON-LD embutido) e para Google Analytics/Meta Pixel. É o trade-off padrão de quem usa essas ferramentas — o comentário no next.config.mjs já registra o motivo. Eliminar exigiria nonces por requisição, complexidade que não se paga aqui.

Dados externos entram no prompt dos agentes

Em lib/agent/prospeccao.ts, dados do prospect (que virão de APIs públicas de CNPJ) são inseridos no prompt via JSON.stringify. Um nome de empresa malicioso poderia, em tese, tentar influenciar o texto gerado. Risco baixo hoje: os agentes estão em standby, e todo rascunho passa por aprovação humana antes de sair. Vale revisar quando ligar a v2.
